### 8) `content_skills` 偶发挂 = 前端加载窗口的点击竞态（本轮唯一产品级 bug）
- 现象：全量回归里 `test_content_skills.py:200` 报 `Expect "#caption" to_contain_text '实际改稿测试'`，实际值停在**上一版** `先做图文不做视频\n\n把范围收窄`（30s 超时）。单独跑 4 次都 62 通过。
- 定位手法（很值钱）：测试的临时库 `%TEMP%\cwb-skills-*` **不会被清理**，直接翻失败现场库即可。锁定 `cwb-skills-rcecspsc` 后看到：**event 表里根本没有 `change_requested`**，platform_revision 只有 3 版（成功的库是 4 版：v1 种子 / v2 标题改稿 / v3 整篇重做 / v4 浏览器改稿）→ 改稿请求**从未到达后端**，前端的失败被 `guard()` 吞成一个瞬时 toast，测试只能看到超时。
- 根因：`ReviewPreview.html` 的模块用**顶层 await** 顺序读接口（`/studio/options` → statusBar → `/contents` → `/contents/{id}` → `/profiles` → `/publications`），而 `page.goto` 等的 `load` 事件在模块初始化完成前就返回。这个窗口里 `#revision-submit` 本来就是可点的（只有 `renderAll()` 里的 `syncRevisionControls()` 才会动 disabled），但 `DETAIL` 还是 null → `requireRev()` 抛错 → 请求发不出去。整机满载（37 阶段串行）时接口更慢、窗口更宽，所以只在全量里偶发。
- 修法（按项目约定"不要让入口可点、点了才报错"）：`ReviewPreview.html` **模块求值时就禁用** `revision-submit / revision-record / skill-audit / btn-illustrate`（抽出 `REVISION_ENTRY_IDS` + `revisionEntries()`，与 `syncRevisionControls()` 共用一份清单），等 `renderAll()` 拿到版本再统一启用。
- 测试侧：`test_content_skills.py` 改为先等 `#revision-message`（明确的成功信号，写明新版本号），失败时把 `#cwb-toast` 的报错文本一并抛出来 —— 免得下次又把"请求没发出去"伪装成一次超时。
- 回归断言：`test_browser.py` 新增 2 条 —— 用 `page.route("**/api/v1/**", 延迟 0.6s)` 把加载窗口**稳定撑开**，断言窗口内四个入口先禁用、详情读回后恢复可用（browser 106 → **108 通过**）。
- 证据脚本：`storage/tmp/_race_probe.py`（修复后：窗口内全禁用、读回后启用 → 顺带证明 `load` 事件确实早于模块初始化完成）与 `storage/tmp/_race_probe_before.py`（用 `page.route` 改写 HTML 把新增那行删掉 → 窗口内四个入口全可点，反证竞态成立，且不用改项目文件）。
