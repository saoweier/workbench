## 为什么说「工程完成」而不是「业务可用」

P0–P3 全程 **未发起任何真实 API 调用、未产生任何费用**。所有模型输出都来自 **fixture（预置样本）**，用于验证管道正确性，不代表真实生成质量。

要变成「业务可用」，需要你（Rosso）做两件事：

1. **配一次真实 Provider Key** —— 适配器代码已就绪，但从未连过真实端点。你说过「P3 走完我再配」，现在可以配了。
2. **核对一次抖音 / 小红书发布界面** —— 确认上传规格（尺寸、格式、文案长度），把 `platform_upload_verified` 从 `false` 翻成 `true`。

这两件事不阻塞 P4 的工程开发，但阻塞「真实试跑」。

## P3 期间修掉的真缺陷（3 项）

1. **`_scan_artifacts` 改了状态却没 commit** —— `with` 块退出即回滚，"已标记为缺图"从未落库，故障被静默吞掉。这是**最危险的一类 bug**：看起来有告警，实际没记。
2. **`/usage` 双真相来源** —— 旧接口读 P0 的 JSON ledger，而 P2 记账已落表，会出现"页面显示 0 消耗、实际已花钱"。
3. **`FABRICATED_EXPERIENCE` 只扫 claims 不扫页面正文** —— caption 里写"我亲测…"当前**漏检**。我把它**如实断言为已知边界**，并写进了前端和报告，没有假装拦住。

> 第 3 条我特意说明：这不是修好了，是**画出了边界**。测试里有一条断言专门锁定"这里目前拦不住"，这样将来真修好了，测试会红，提醒我们去更新说法。

P4 是**唯一一个「往回走」的阶段**——前面所有阶段都是"把内容造出来"，P4 是"看它跑得怎么样"。

| 任务 | 内容 | 关键约束 |
